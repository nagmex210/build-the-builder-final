## Idea

After the account is loaded, the call goes through three kinds of node:

- **ROUTER (triage only).** It states the debt and routes. It holds no negotiation rules, makes no offers and has no promise tool.
- **`negotiate` (the main path).** It holds all the promise logic.
- **One specialist per exit situation.** Each exit is reached by a tool-call transition whose trigger is named. Every route out (router or negotiate) has the same exits, because cannot-pay or a plan request can come up mid-negotiation (M22).

Code makes each specialist start with the brief's own clause for its situation, for example the "make no persuasion attempt" clause in hardship. "Once only" applies per call: an offer, the sympathy sentence or a question is made at most once per call, even when the specialist is entered again (M21/M31). In a situation where the brief records a promise only when the customer names one, the specialist never proposes a date or amount.

Everything is read from the brief at build time. Nothing is hard-coded.

## What changed (files)

- **`builder/situations.py`**, ported from idea/b5-3 and extended:
  - The extraction now also returns, per exit:
    - `first_line`: the brief's governing clause, in its own words;
    - `once_only`: the brief's once-only limits;
    - `promise_allowed`: never, only if the customer names one, or yes.
  - New deterministic, idempotent `apply(wf, spec)`, run in the final pass from `save.py`. It does two things:
    - It prepends a `## THIS SITUATION (from the brief)` block to each specialist's task_message. The block holds the FIRST RULE (the brief's clause), the respond-once rule, "every offer/question at most once per call (also on re-entry)", ONCE PER CALL lines and the PROMISE rule.
    - It appends a silent HAND-OFF rule to every node that routes to a specialist.
  - `check()`: a coverage check (from b5-3) plus a new structural test. It flags a router that is not triage-only: a node routes to specialists but there is no separate main-path node.
- **`builder/build.py`**:
  - The situations extraction runs in parallel with datecalc.
  - The prompt gets the situations block, and the build agent must run `situations.py check` before every save.
  - The trace gets `test` events: the situations extracted, and the coverage check of every final pass.
- **`builder/save.py`**: calls `situations.apply` after `canned.apply`.

## Brief-agnostic?

Yes:
- The situations, their triggers, governing clauses, once-only limits, promise rule, tools and close values are extracted from the brief and the tool API file at build time.
- `apply` and `check` are structural: node keys come from the extraction, and there are no tool, value or outcome names in the code.
- The router/specialist recipe in routing.md is written for any collections brief.

On rB, the extraction produced the same situation kinds from raw bank material as from the clean briefs.
