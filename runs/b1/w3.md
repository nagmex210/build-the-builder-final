# b1 / worker 3: code steps for dates, business days, deadlines, floors

## Idea

The phone agent model is bad at calendar math (seen: it read back "today, Friday 2025-10-31" for a call on
2026-10-14 and recorded that date). So the builder computes every date and amount fact in code that it
generates from the brief and tests before Claude assembles the workflow:

1. `builder/datecalc.py`: one Azure call (`tier=strong`, traced) extracts a small **calendar/amount spec** from the
   briefs + tool API file: weekend days, holidays, deadline bands (selector field, min/max, N business/calendar
   days, attempts, optional product types), floors per product type (field / percent of field / fixed / minimum),
   callback window (days ahead, from/to, after now), meaning of "this/next <weekday>", the account tool and its
   product list key/fields. Raw briefs work too (memo overrides are in the prompt).
2. Generic Python templates (no brief values in them; spec is embedded as hex so no `{{`/`}}` appears) produce:
   - a **code node** that writes `date_facts`: TODAY, tomorrow, next business day, last business day of
     this/next week and month, deadline per band, callback days, a "this/next <weekday>" table, and a day-by-day
     CALENDAR up to the furthest deadline (business day flag, holiday/weekend -> next business day, deadline and
     after-deadline tags);
   - a **post_process_code hook for the account tool** that adds to every product `band`, `deadline`,
     `deadline_weekday`, `persuasion_attempts`, `floor_amount`, and puts the full DATE FACTS block into the tool
     result (`data.date_facts`) and into `vars['date_facts']`.
3. Both snippets are executed locally on 5 dates and fake products (one per band); a crash or missing deadline
   retries the extraction once; result logged as a `test` event in the trace.
4. `builder/build.py` runs datecalc first (~8 s), then tells Claude (build-phone-agent skill) to put the code node
   as start node, the hook verbatim on the account tool, `{{date_facts}}` in date-handling prompts, and "never
   compute a date yourself; look it up".

Iteration 2 (after reading transcripts): in a live call the start code node left no trace and the model invented
today's date, while the account hook worked (it returned the correct `deadline 2026-11-02`, `floor_amount 126`).
So the hook now also returns the whole DATE FACTS block (the reliable copy after identity).

## Files

- `builder/datecalc.py` (new), `builder/build.py` (runs datecalc, extra build instructions, trace event).

## Brief-agnostic?

Yes. No date, holiday, band, field name, product type or amount is in the code or prompts; all come from the
extraction at build time. The extracted spec for A, B, raw-A, raw-B was identical in substance (same holidays,
bands 1-7/8-45 -> 12/7 business days, floors minimum_payment / instalment_amount, callback today+1 business day
10:00-19:00). Unknown deadline units or rules fall back to the brief text (the facts are additive).

- A PUB-02 [asks_back/plain probe]: the judge said "next business day is 12 Oct" on a 14 Oct call, while the agent

- B PUB-11/12: the agent made up product ids (`CC_12345`, `cc_9015`) for create_promise/add_note. B PUB-13: the

- rB PUB-13 [talkative]: the loan was recorded at 400, but 900 was expected (amount handling, not the deadline).
  The date (the 23 Oct deadline) was right.

## Build time

datecalc step 7-10 s (one Azure call + local tests). Whole builds: 159-737 s (B was slowest: Claude spent time
probing the 503s). Note: v2 builds of A/B reused the v1 `out/<slot>.workflow.json` from the same slot and only
swapped in the new code; a fresh build behaves like v1 + the hook date facts.

## Open questions / hypotheses for the merger

  `code_exec` event in the call, model invented the date). If true, the pre-identity date facts (callback day)
  are missing; fix = put the code node after the first conversation node, or add the same snippet as a
  `pre_process_code` of the first tool called. The account hook copy works (seen in the call log).
- (hypothesis) A `pre_process_code` on `create_promise` / `schedule_callback` could check the date against
  the same spec (business day, <= product deadline, inside callback window) and return a clear error to the
  model instead of recording a wrong date. Not built here.
