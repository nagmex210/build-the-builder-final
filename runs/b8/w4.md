## Idea (one)
On the latest brief C fast runs (runs/b6/merge/fe-C2, fe-C2-adv, fe-C3), the most frequent builder-side kind is the
**invented floor**. The agent names a small round "minimum" (50 / 100 / 150) instead of the computed floor: C-05 and
C-10 in all 3 runs (6 of ~33 failing runs). It is also the top open fast failure on A in mechanisms.md (M27 amounts:
"still open, no fix on any branch"), and PUB-06 "floor offered twice" fails 1/2 in every official A run.
The date half of M27 was already fixed by the code-only `check_promise_date` tool (dates ~38 -> ~8). I extended the
same tool to amounts, so the amount to OFFER comes from code too.

I did not read brief C or put anything from it in builder/. I used only the eval rows' failure lines (as
mechanisms.md does).

## What changed (builder/guards.py only)
- `check_promise_date` takes an optional `amount` (and `date` is now optional; `required: [product_id]`).
  - The customer names an amount, or says they cannot pay the full amount (amount 0): code answers
    CAN BE RECORDED (keep it), CANNOT (more than the full amount: the maximum), or
    "CODE COMPUTED THE LOWEST AMOUNT for product X: <floor>" (`lowest_amount`). The floor comes from the same
    `guard_products` (datecalc `floor_for`, the brief's rounding) that the promise guard uses.
  - It counts floor offers per product in `vars['floor_offered']` (M21). On a second ask it answers "ALREADY offered
    in this call: do not offer it again (unless the brief explicitly allows a repeat) ... follow the brief's next
    step". The first answer says that naming the floor once IS the one offer.
  - An unknown product id is answered with the listed ids (seen live: the model sent `CC_1903` / `PL-9021`, got the
    list, retried with `p1`). This also helps M7.
  - Amounts are formatted for speech: 700 / 637.50, not 700.0.
- Every node that has the check tool gets an "AMOUNT CHECK IN CODE" line: call the check before naming any lower
  amount; the only lower amount you may name is `lowest_amount`. The line is added on its own, so it is not lost when
  the node already mentions the check tool (v1 missed it on rB).
- Tested locally by running the generated hook on A's real spec: none / below floor / allowed / above max /
  date+amount / unknown id / unresolved `{{amount}}` placeholder.

## Brief-agnostic?
Yes. The hook reads only the brief-derived spec (`guards_products` from datecalc floors/max, built from the brief at
build time) and the tool's own body. It has no product types, amounts, codes or wording from A/B/C. The "once"
behaviour respects "unless the brief explicitly allows a repeat", so briefs with several persuasion attempts per
product are not overridden.
