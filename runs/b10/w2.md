## Live platform probe (new fact, runs/b10/w2/probe/)

A 1-node workflow with a tool whose pre-hook writes `pre:<label>` and whose post-hook writes `post:<label>` into vars
and returns the trace. In one chat turn the model called it three times in parallel (alpha, beta, gamma).
Result (probe_events.json, call 862e5d9b):
- alpha `pre:alpha post:alpha`
- **beta `pre:alpha post:alpha`**
- gamma `pre:gamma post:gamma`

So **in a parallel turn, a post-hook can read a sibling's vars instead of its own pre-hook's writes**. beta's
post-hook never saw `pre:beta`; it saw alpha's state. Also, **`config` is not available in post-hooks** ("noconfig"),
so a post-hook cannot read its own request. Any per-tool flag carried from pre to post (guard_block_*, dup_hit_*,
write_req_*, guard_check_result) can belong to another call in such a turn. This is the M20 mechanism, now measured
directly. The identity gate's post-hook reads `globals().get('config')` and therefore always falls back to
`last_request_*`.

## Reported only (not confirmed, not fixed)

1. **Placeholder fill from the previous call's args.** If the model omits a body field, harden's pre-hook fills the
   literal `{{field}}` with `vars['<tool>_args.<field>']` first. The docs say each call overwrites `_args`, so on a
   multi-product turn this may be the OTHER product's value (an amount or date bound to the wrong item). No bare
   variable clashes with a body field name in A/B/rA/rB builds, so the risk is only `_args`. Needs a live call where
   the model omits a field.
2. **No failure route out of the account lookup** (`load_account` has only `always -> router`). A failed get_account
   enters negotiation with no data (M54). The mock never fails get_account, so it is not reproduced.
3. **check_promise_date shared slot** (`guard_check_result`): with the probe's sibling-vars behaviour, parallel
   checks can show one product's answer for the other. This is mitigated, not fixed: `say` names the product, and the
   tool description says one call per message.
4. **dup_hit_ flag across siblings**: a NEW add_note (bare `{ok:true}` answer) next to a re-sent one may be answered
   "ALREADY RECORDED". The text stays true (it was recorded), but writes_ok misses it.
5. **One failure count for rejections and outages**: one rejection plus one 500 reads "failure number 2". The model
   may then close as service_error after only one real outage.
6. The canned say_now `<<placeholder>>` loose match can pick a short field (`ok` is in `booking`). This is
   theoretical; no current brief line has such a placeholder.

Carry-over still not on main and the biggest workflow-side bug I know: **M59, chat skips the initial node**
(idea/b9-5 livevars, repro on C-01). Every fast_eval runs with no DATE FACTS until a tool result brings them.

## Brief-agnostic?

Yes. Every fix reads only the workflow's own tools, the tool API file (success id fields, selector enum) and the
shape of the bank's answers. No brief rule, value, name, date or outcome code appears in the code. R5 opens the gate
only when the bank gives NO call-wide flag and every question the API lists passed. R7 matches an id only against
the text fields of rows the lookup returned.
