# b1 / worker 1: brief extraction → structured rule spec before building

## Idea
Before the Claude build agent starts, `builder/extract.py` turns the brief files (a clean spec, or raw mail + policy
extract + memo + code sheet) plus the tool API file into ONE rule spec in a fixed outline (`out/<slot>.spec.md`):
sources and precedence with every override listed as `OLD -> NEW`, call variables, the 7 tools (fields/enums/hints),
opening/third party, identity, disclosure/products, promises with date/amount rules as **formulas**
(`latest_date = add_business_days(today, 12)`), calendar with every holiday, special situations, the exact
outcome/reason table, honesty rules, a **numbered rule checklist** (R1..Rn with source clause) and ambiguities.
Pass 1 = extract (Azure strong tier, gpt-6-astra); pass 2 = a verifier that re-reads the sources against the spec
and outputs a corrected spec plus a `Verifier corrections` section. The Claude build prompt then points at the spec
("read it first, build from it, the brief wins where the spec is clearly wrong"), and SKILL.md step 7 now checks the
workflow against the spec's numbered checklist.

## Files
- `builder/extract.py` (new): outline, extract and verify prompts. Nothing brief-specific.
- `builder/build.py`: runs the extraction (trace event `spec`), adds the spec to the prompt; `--spec` reuses an
  already extracted spec (dev reruns only); prompt now forbids running `tools/run_cases.py`/practice cases and
  reading other slots' files in `out/` (both happened in my builds, see below).
- `.claude/skills/build-phone-agent/SKILL.md`: steps 1 and 7 use the spec.
- `btb/llm.py`: `chat(..., timeout=)` parameter (default 180 s, unchanged). Extraction needs about 600 s.
- `btb/fast_eval.py` (harness, **merger please review**): a 503 from `/chat/message` is now retried like 502/504
  (5 tries, with backoff). Without this, almost every case failed at turn 0 with a platform 503 while six workers
  were evaluating (my first two evals: 0/10 and 0/3, nearly all `harness: 503`). Same safe path as before:
  resend only if there is no call yet; otherwise wait for the reply.
- `runs/b1/w1-specs/*.spec.md`: the four extracted specs, so they can be inspected.

## Spec quality (checked by hand on raw A)
The memo override was applied correctly: the early/late deadlines show the amended values everywhere, section 0 lists both
overrides, and the verifier also removed an invented week-boundary rule and an invented "API wins" rule. The specs
are 60-77 KB, so they are long.

## Build time: over budget
- Extraction: 406-554 s (pass 1 about 4 min, verify about 4 min; gpt-6-astra, 60-77 KB out).
- Claude build after that: 766-1266 s. w1-B and w1-rA reused the spec via `--spec` (1241/1266 s on their own,
  so about 1700-1800 s with extraction counted). w1-rB was a full run: **1321 s in total, including 554 s of extraction**.
  I stopped w1-A at about 27 min of Claude time plus 7.5 min of extraction, because it was self-testing with chat scripts.
  Its saved workflow (version 3) is what got scored.
- Because of this, the idea as it stands puts a build at risk of the 30-minute limit. Fix: run extraction with
  `effort="low"`, or skip the verify pass, or run verify in parallel with the start of the Claude build.

## Failures left (not extraction-specific)
- B and raw-B: multi-product flow. Promises are recorded per product with repeated or failed `create_promise`
  calls, the agent reads back or confirms each product separately instead of once together, and the honesty judge
  flags a "recorded" claim made before the tool call. In PUB-11, identity ended `not_verified/declined` after the
  simulated customer gave wrong phone digits and then said "not sure".
- raw-A: `create_promise` loops (PUB-06: 11 calls), double `close_call`, calls that never close.
- A: PUB-02 callback (0/2), PUB-03 (a 4th `verify_identity`, then a promise after the 3rd wrong answer), PUB-06.
- The inner Claude **ran `tools/run_cases.py`** (rA, twice; I killed it) and read `out/w1-rA.gen.py` from
  another slot (rB). The prompt now forbids both. That change is committed but untested.

## Brief-agnostic?
Yes. The outline lists only the kinds of things every collections brief has (variables, tools, identity, promises,
calendar, outcome table). Every value comes from the files at build time, and the prompts name no rule, value,
code, date or holiday from brief A or B. The verify pass is also generic (overrides applied, codes exact, nothing
invented).

## Verdict
The spec it extracts is accurate, including memo overrides in the raw material, but the score was not measurably
better (3/26), and the run was noisy because of platform 503s. The extra 7-9 min of build time is a real cost.
Recommendation: keep `extract.py`, but run it with low effort and a single pass (or verify in parallel), and combine
it with ideas that make the workflow robust (code steps for promises and multi-product, a guard against repeated tool calls).
I did not iterate: one build cycle takes about 30 min and the worker limit did not allow a second one.
