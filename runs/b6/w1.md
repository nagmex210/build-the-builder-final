# b6 w1: tool-call robustness: idempotent writes in code + build-defect checks (API required fields, hook dry-run)

Branch idea/b6-1, started from main (f4dbaf0). Commits: idempotent writes + apicheck + hookcheck, then two small
follow-ups (the "already exists" answer names the values on record; "the call is already closed" is never read as an
earlier success; that last one landed AFTER the four builds below, so they run with the looser match).

## Idea

1. Idempotent writes (M12 kind, brief C's "duplicate create_promise after success -> already exists -> service-error
   note"). In `builder/harden.py` (every write tool, any brief):
   - pre-hook: key = tool + the request's own `*_id` fields except customer_id (the product id read from the request,
     after the id repair); value = the request's fields except free text (strings of 4+ words), numbers normalised.
     If the same key already SUCCEEDED in this call with the same value, the request goes to the host's no-op path
     (found at build time by `guards.find_noop`, the same probe the guards use; nothing reaches the bank).
   - post-hook: that no-op answer becomes `ok: true, already_recorded: true` + the ids of the first answer +
     `tool_outcome: "ALREADY RECORDED earlier in this call: do not send it again. ... it IS recorded ... This is not
     a failure: never tell the customer it could not be saved and never treat it as a service error."` A bank refusal
     whose error says exists / duplicate / already (not "already closed") after OUR OWN success for the same tool+product
     is read the same way, naming the values on record (the bank keeps the first ones).
   - each successful write (not a guard-blocked one) is stored in `vars['writes_ok']`.
   - guards.py: the promise/callback guard skips an identical re-send (no "NOT RECORDED" for something that is on
     record); canned.py: no `say_now` for an ALREADY RECORDED result (the line was said the first time).
   Tool names never appear: everything is keyed by the request's own tool name and fields.
2. Build defects that killed official B 0/3 in the b5 merge. **The journal's diagnosis was wrong.** I fetched a
   self-sim call of that build (workspace 2): `customer_id` WAS in every verify_identity request. The real cause:
   the inner build agent's post-hooks ended with `_wn(response, _m)`; a post-hook's input is `result`, so every call
   raised `NameError: name 'response' is not defined` -> platform `function_call_error` -> "I had a technical issue"
   -> nobody passed identity (7 hooks on 6 tools, `/home/ubuntu/btb/repo/out/main-B.workflow.json`). The fix round
   then "fixed" the required list (not the cause), round 2 was still 11/12, and the revert went back to the
   equally broken build version.
   - new `builder/hookcheck.py`: dry-runs every api_call tool's pre/post hook in a sandbox (sample success and failure
     results, sample request); `errors()` is a lint ERROR in the build trace; `repair()` (in `save.finish_and_save`,
     before harden, on every save) prepends `response = result` (or the usual aliases) when that NameError is the
     cause, else wraps each top-level statement in its own try/except so our honesty/guard/id blocks still run.
     On the b5 broken workflow: 7 errors before, 0 after (`response = result`).
   - new `builder/apicheck.py` (the item as assigned): every tool whose url ends with an API path keeps every field
     that path's request body requires (properties + required list); missing ones are put back with
     `"default": "{{field}}"`. Lint ERROR in the trace, repair on every save. The API file path reaches save.py via
     `BTB_TOOLS_API` (set by build.py). Note: the kit's own example also lacks `customer_id` in `required` and works;
     the field is sent as long as the leaf has a default, so this check is a safety net, not the b5 cause.
   - "ship the best self-sim version": already in build.py (round 2 worse -> restore the build file); it fired on 2/4
     builds here (B: 3/10 -> 7/12 restored; rA: 6/12 -> 9/10 restored). With the repairs in `finish_and_save`, the
     restored version is repaired too (the b5 failure was that both versions were broken).
   - SKILL.md: two lines (ALREADY RECORDED is success; hooks use `result`/`config`, keep API-required fields).

**The evaluated builds carry a bug of this change, fixed in the last commit but NOT re-measured (no time):**
`verify_identity` is not a `get_*` tool, so harden treated it as a write. In rA PUB-04 the model re-sent the passed
date-of-birth check in the same turn as the phone check: the re-send was correctly answered from the no-op, but the
per-tool `dup_hit` flag is shared by the parallel sibling (M20), so the REAL phone-check answer was also replaced by
ALREADY RECORDED; `all_verified` never reached routing, the account was never loaded, the model said "technical
issue" and closed `service_error`. The many `no_promise/service_error` closes on rA (5 reps) and B (3 reps) are
probably this. Fix (commit after the report draft): only acknowledgement-shaped successes (`ok` + `*_id` keys) are
remembered, so check/verify tools are never deduplicated; and a result is only read as the no-op answer when it is
the no-op's bare `{ok}` body, so a parallel sibling of the same tool keeps its own result. Local exec tests pass
(identical create_promise re-send -> no-op; verify_identity twice -> both real results). **Merger: rebuild before
judging this branch; the numbers above under-state it.**

## Brief-agnostic?

Yes. Dedup keys are the request's own tool name and `*_id` fields; the no-op path is probed on the tool's own host;
the duplicate match is on the bank's error words (exists/duplicate/already), not on any brief text. apicheck reads
only the tool API file given to the build. hookcheck only executes the workflow's own hooks on synthetic inputs.
Nothing from brief A/B is in the code or prompts.
