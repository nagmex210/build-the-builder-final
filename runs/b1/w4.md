# b1 / worker 4: honesty and tool-call robustness

## Idea
Make honesty and failed-tool handling **structural, not prompt-only**: after the builder model writes a workflow,
a deterministic step (`builder/harden.py`) rewrites every `api_call` tool so that the agent model can never
misread a tool result:

- **post-hook on every api_call tool** (node `tools`, `pre_actions`, workflow-level tools): any failure (HTTP >= 400,
  envelope status not success, `ok: false`) gets a `tool_outcome` line in the result: `FAILED: <tool> was NOT carried
  out and NOTHING was recorded (error: ...). This is failure number N of <tool> in this call. Never tell the customer
  it was recorded ... Apply the brief rule for a failed tool call ...`. It also keeps a per-tool counter in
  `vars['tool_failures_<tool>']` that routes can use. Pure-acknowledgement writes (`{ok, *_id}` responses) get a
  `SUCCESS: ... Only now may you tell the customer it is recorded. Speak to the customer now.` line (also fixes the
  "silent after tool result" problem from the docs). Headers are dropped.
- **ids from the account lookup**: the post-hook of every `get_*` tool collects every `*_id` value in the response
  into `vars['known_ids']`; a **pre-hook on every write tool** repairs an id field the model filled wrongly (case
  mismatch, or the only id there is). On an id error, the FAILED line lists the valid ids.
- **no silent platform retries on writes** (`maxRetries: 0` on every non-`get_*` tool): the brief's own retry rule is
  carried out by the model, visible in ledger + transcript (a platform retry would hide a `fail_first_n: 2` case).
- **skill section "Tool failures and honesty"**: tells the builder model to read `tool_outcome`, to write the
  brief's failed-call rule (attempts, wording, closing outcome) into every node with a write tool and into routing
  (OR of engine `<tool>_failure_count` and hook `tool_failures_<tool>`), to never announce a record before SUCCESS,
  and to take ids only from the lookup result.
- Saves go through `builder/save.py` (harden + save); `build.py` re-hardens and re-saves the final file anyway, so the
  published workflow always carries the hooks, whatever the builder model did. Logged in the trace (`harden+save`).

## Files
- `builder/harden.py` (new): the hooks + `harden(workflow)`; idempotent (does not add twice, keeps the builder's own
  hooks: ours run after its post-hook and before its pre-hook).

- `builder/build.py`: final harden + save + trace event.

## Brief-agnostic?
Yes. harden.py reads only the workflow's own tool names and the generic response shape (`ok`, `error`, HTTP status,
`*_id` keys); it contains no rule, value, product, queue, outcome code or retry count from brief A/B. The retry
count and the failure outcome stay in the brief and are compiled by the builder model from whatever the brief says
(the skill gives "try once more, then say it could not be done" only as a fallback when a brief is silent). The only
assumptions are the kit's fixed conventions: read tools are named `get_*`, ids end in `_id`.
